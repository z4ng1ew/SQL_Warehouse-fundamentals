## Сначала — что такое обычные ключи

**Primary Key** (первичный ключ) — это столбец (или набор столбцов), который **однозначно** идентифицирует каждую строку в таблице. Главное правило: значения **не могут повторяться** и **не могут быть NULL**.

```sql
-- У каждого пользователя уникальный ID
CREATE TABLE "user" (
    id bigint PRIMARY KEY,  -- 1, 2, 3... каждый встречается РОВНО один раз
    name varchar,
    lastname varchar
);
```

**Foreign Key** (внешний ключ) — это столбец в одной таблице, который **ссылается** на Primary Key другой таблицы. База данных сама проверяет, что ссылка валидна (referential integrity — ссылочная целостность): нельзя вставить в Balance запись с `user_id = 999`, если в таблице User нет пользователя с `id = 999`.

```sql
-- currency_id ссылается на id в таблице currency
CREATE TABLE balance (
    user_id bigint REFERENCES "user"(id),      -- foreign key
    money numeric,
    currency_id integer REFERENCES currency(id) -- foreign key
);
```

## Что такое Mocked Primary Key (мнимый первичный ключ)

**Mocked** в переводе с английского — «подделанный», «имитированный», «ненастоящий». Это **не** стандартный термин SQL. Это термин из задания, придуманный авторами для объяснения ситуации.

Суть вот в чём. В исходной базе (Red Source) у Currency был нормальный Primary Key:

```
ID = 100, name = EUR, rate_to_usd = 0.9
```

Одна строка на одну валюту. ID = 100 — уникален, всё по правилам.

Но когда данные перенесли в DWH и добавили колонку `updated`, **тот же ID стал повторяться**:

| ID | name | rate_to_usd | updated |
|-----|------|-------------|---------|
| 100 | EUR | 0.9 | 03.03.2022 13:31 |
| 100 | EUR | 0.89 | 02.03.2022 12:31 |
| 100 | EUR | 0.87 | 02.03.2022 08:00 |

ID = 100 встречается **три раза**. Значит, это уже **не настоящий** Primary Key, потому что нарушено главное правило — уникальность. Столбец `id` всё ещё **выглядит** как первичный ключ (те же значения, тот же смысл — идентификатор валюты), но **не работает** как первичный ключ.

Поэтому его и назвали **Mocked** — он «притворяется» первичным ключом, но на самом деле им не является.

## Почему так произошло

Потому что обычная реляционная модель превратилась в **темпоральную** (Temporal Model). В темпоральной модели настоящим уникальным идентификатором строки является **пара** столбцов: `id` + `updated`. Именно эта пара неповторима — не может быть двух записей с одинаковым ID **и** одинаковым временем обновления.

## Почему в задании нет настоящих Foreign Key

В задании связи между таблицами названы **«Virtual Foreign Key»** (виртуальный внешний ключ). Это значит, что `balance.currency_id` **по смыслу** ссылается на `currency.id`, но база данных **не проверяет** эту связь. Нет конструкции `REFERENCES`. Поэтому возможны аномалии: в Balance может быть `currency_id = 500`, а в Currency такого ID нет вообще. И это **нормально** для данного задания — ты должен обрабатывать такие случаи через `LEFT JOIN` и `COALESCE`.

## Итого в одной фразе

Primary Key — настоящий уникальный ключ. Mocked Primary Key — столбец, который **был** первичным ключом в источнике, но в DWH перестал быть уникальным из-за добавления истории изменений. Foreign Key — ссылка на другую таблицу, которую проверяет база. Virtual Foreign Key — ссылка по смыслу, но база **не проверяет**.
